## site-keys / 便签本 · Sticky v4.1：记事本导入 txt

- **需求**：用户要求给记事本模块加「导入 txt」，同时问 md 渲染是否会有较大性能开销。用 grill-me 追问，Q1 用户选 1（一个 txt = 一篇新文档，文件名作标题、支持多选、不追加不覆盖）；B~E 由代理按推荐一次性收口，用户回「那你先做导入 txt 吧，按 1」后开工。
- **md 性能结论（重要，后续别重复论证）**：性能不是瓶颈。当前产物 JS 85 KB / gzip 32 KB；`marked` ≈ 40 KB、`markdown-it` ≈ 110 KB、`DOMPurify` ≈ 22 KB，对本地 unpacked 扩展加载无感；解析 O(文本长度)，单篇毫秒级，debounce 即可。真正贵的是两点：① `v-html` 会让 Markdown 里的 `<img src=https://…>` 发网络请求，破坏「零网络」硬约束；② 需要「编辑/预览」切换，破坏已确认的「整页都是编辑器」形态。**另外发现一个比 md 更严重的既有坑**：`saveWorkspace` 每次输入序列化整库，导入大文件后每敲一个键都会卡，且 `storage.local` 配额约 10 MB —— 本轮用 1 MB / 20 个上限压住，未重构存储。
- **实现**：新增 `src/core/textFile.ts`（`decodeTextFile` / `titleFromFileName` / `isTxtFile` / `planImport`，常量 `MAX_IMPORT_BYTES=1MiB` / `MAX_IMPORT_FILES=20` / `TXT_ACCEPT='.txt,text/plain'`）；`useWorkspace.importDocs()` 倒序插队、整批一次落盘、自动切到第一篇；`App.vue` 两处 `.file-new--sub`「导入 txt」按钮 + 单个隐藏多选 file input；`base.css` 加次级按钮样式。权限保持 `storage, sidePanel`。
- **编码策略**：BOM(UTF-8/UTF-16LE/BE) → 无 BOM UTF-16LE 的 NUL 比例特征 → `TextDecoder('utf-8',{fatal:true})` → 失败回退 `TextDecoder('gb18030')`。正文原样，不做 CRLF 归一化。
- **守卫修订**：`SPEC.md` §1 非目标从「CSV/JSON 导入导出」细化为「批量数据导入导出 / 备份」并显式豁免 v4.1 的 txt 只读入；`tests/security.test.ts` / `tests/design.test.ts` 里 v4.0 的 `not.toContain('type="file"')` 改为「必须含 type=file + 只收 txt，且禁 导出/download/v-html/Markdown 库」。踩过一个真实误伤：新模块注释里写 `chrome.*` 字面量被 core 纯逻辑守卫判为引用浏览器 API，改措辞后通过。
- **验收**：按 TDD 先跑真实 RED（模块不存在 + 2 条守卫失败）→ GREEN；9 测试文件 / **114 用例全绿**，`typecheck` 零错误，`build` 成功；主 JS 89.7 KB（gzip 33.4 KB），产物无 fetch/XHR/scripting/v-html/Markdown 库/外链。用无头浏览器 + Vite 预览页注入 `DataTransfer` 跑通完整链路：2 txt + 1 md → 2 篇文档、标题取文件名、自动切第一篇、正文原样、GBK 解码为「中文测试」、md 跳过并提示；截图 `design/render/05~07`。
- **未声称通过**：Chrome 扩展环境里真实点击系统文件选择对话框、`storage.local` 持久化、刷新后内容保留，仍未真机确认，README/SPEC 已如实标注。
- **文档**：`SPEC.md` v4.1、`README.md`、`docs/TICKETS.md`（新增 T-38 与偏差 9~11）、根 `README.md`、`package.json` / `public/manifest.json` 版本 0.4.1 同步。

## site-keys / T-40：v4.2 分键增量存储（用户问「能不能换 SQLite」）

- **需求**：用户担心「都存浏览器会影响性能或者长期会丢数据」，问能否弄个 SQLite。核查后给结论并出四选项，用户选「按推荐修性能（推荐）」。版本 0.4.1 → **0.4.2**。
- **结论（后续别重复论证）**：① 性能瓶颈是 `App.vue` 每次 `@input` → `saveWorkspace()` 整库序列化，与存储引擎无关；② `chrome.storage.local` 配额 10 MB（Chrome 113 及更早 5 MB），而导入上限 1 MB × 20 可累计超配额，`set()` reject 只弹 5s toast → 看着存了、刷新才发现没存；③ **SQLite 治不了长期丢数据**：OPFS / IndexedDB 同属扩展 origin，卸载 / 删 profile 一起清，磁盘压力下还可能被回收；标准 SQLite WASM 要 COOP/COEP + SharedArrayBuffer，OPFS 独占锁会和「侧栏 + 全屏页同时打开」撞锁；④ 真正防丢只能把数据写到扩展沙箱之外（导出 / 授权目录 / native host），本轮明确不做。
- **实现**：`core/storage.ts` 改为 v3 布局（`sticky.workspace.v3` 只存 id 顺序 + `sticky.note.v3.*` / `sticky.doc.v3.*` 每条目一键），`KeyValueStore` 增 `getAll/setMany/removeMany`（平台侧对应 `get(null)/set(items)/remove(keys)`）；v3 meta → v2 整库 → v1 旧库三级迁移，**先写新键成功后才删旧键**；内存 `WorkspaceFile.version` 仍是 2。状态机改增量提交：改一条只写那一条（连 meta 不动），新建 / 删除 / 导入把 meta + 条目放进同一次 `setMany`；写盘成功后才更新内存镜像。UI 加 250ms debounce（按条目 key 合并快照）、`blur`/`visibilitychange`/`pagehide` flush、`runAction()` 排队、持久「改动没有保存」条幅。权限加 `unlimitedStorage`。
- **TDD**：先写 `tests/incremental.test.ts` 18 条守卫跑真实 RED（17 失败）→ GREEN；同步修订 `storage/import/useWorkspace/manifest` 四个测试里对旧整库键与两项权限的断言。
- **验收**：11 文件 / **137 用例全绿**，typecheck 零错误，build 成功，主 JS 92.6 KB（gzip 34.3 KB，仅 +2.9 KB，零新依赖）；产物审计无 fetch/XHR/scripting/v-html 等。真实浏览器注入假 `storage.local` 实测：连打 5 次 → 输入期间 0 次写、debounce 后 1 次写且只含 1 个条目键；模拟写入失败 → 持久条幅出现，重试成功后消失，落盘标题 `retry-ok`。临时 `_harness.html` 已删、静态服务已停。
- **文档**：SPEC §4/§7.5/§9/§11/§12、README（数据表 / 风险 / 验收）、`docs/TICKETS.md` T-40 + 偏差 12~14、根 README、图标预览版本标签同步。
- **仍存在的风险（如实写进 README/SPEC）**：卸载扩展 / 删 profile 仍会丢全部数据（用户本轮没要备份）；debounce 250ms 窗口内进程被强杀可能丢最后一点输入；真机 Chrome 扩展环境手工验收仍未执行。用户需在 `chrome://extensions` 重新加载 `dist/`，首次打开会自动迁移旧数据。
- **注意**：Chrome 会缓存扩展图标，用户需在 `chrome://extensions` 点「重新加载」，工具栏仍显旧图时移除后重新加载一次；真机图标刷新未声称通过。未做页面 favicon / 深色反色版 / SVG 版（扩展页未指定 favicon 时 Chrome 沿用 manifest 图标）。
